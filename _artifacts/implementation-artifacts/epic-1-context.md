# Epic 1 Context: Fondasi — Instalasi, Kontrol Akses & Pengaturan Sistem

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Give a Developer a working, installable admin backend and give every later epic its shared foundation. A Developer installs Bazaar into an existing Laravel + Filament client project via Composer and one Artisan command — no new panel, no greenfield scaffold — and gets a functional panel where Staff can log in. Access is governed by dynamic Role & Permission (no hardcoded roles), every mutating action is automatically recorded in an immutable Audit Trail, and operational parameters are configurable through Global Settings without a deploy. This epic also builds the shared substrate every later epic depends on and never rebuilds: the DESIGN.md token system as a Filament theme override, the core reusable UI kit (Data Table, Modal, Toast, Tabs, Pagination, Empty State, Alert Banner, Dropzone), the global IA shell (sidebar/topbar), bilingual EN/ID + dual light/dark theme, an internal-tool accessibility floor, the two integration paths (Service Layer for monolith portals, optional Sanctum API Layer for headless portals), and the one shared media-optimization (compress + WebP) pipeline used by every image upload across the whole package.

## Requirements & Constraints

- Bazaar is a Composer package installed into an *existing* client Laravel + Filament project — never a new-app scaffold. Installation connects to the client's existing panel; it never creates a second one.
- Migrations for this epic cover only User & Access + Global Settings; each later epic adds its own migrations independently, not all at once here.
- Users (internal Staff) are a fully separate realm from Customers — no shared table. A User must hold at least 1 Role; a Role with no holders is still valid.
- "Approval Role" is never a hardcoded role name anywhere in the system — it always means "whichever Role currently holds the relevant permission" (publish Item, moderate Review, approve Cancel/Retur, approve Refund, etc.). Permission changes to a Role propagate instantly to every holder.
- Deactivating a User revokes access immediately but must never remove or alter their historical Audit Trail entries.
- Audit Trail is fully read-only in every UI, for every User including admins — no edit/delete control may ever exist for it. It auto-captures who/what/when/before-after for every create/update/delete across every domain, without per-domain manual instrumentation, and is filterable by User, entity, and date range with standard pagination.
- Global Settings is List+Edit only — Staff can never add or remove parameters through the UI. Required parameter groups: Timeout Timer family (OTP, payment deadline, review-submit deadline, tokenized-link access default H+5, On-Process window, auto-confirm), Payment Gateway config (enable/disable + credentials + which specific payment methods are exposed to Customers — never a gateway's full method list by default), Shipping config, Default Warehouse pointer, General Store Info, Minimum/Maximum Refund %, Robots.txt free-text content, Analytics Verification Codes (GSC/GA4/Facebook Pixel). Credential fields (gateway keys) must be stored encrypted.
- Global SEO Defaults (part of Global Settings, not a separate module) holds the fallback chain's last resort: default meta title template, default meta description, default OG image — used only when an entity (Item/Blog/Page/Category) has no image/metadata of its own.
- Service Layer integration lets a monolith (Blade+Livewire) portal call any domain's Service directly via DI/facade, with zero HTTP involved.
- API Layer is optional and off by default (`bazaar.api.enabled`); when enabled it authenticates via Sanctum (a per-service token, not a per-Customer token) and returns API Resource responses exposing the same Service-layer capabilities. Regardless of this flag, Payment/Shipping webhook ingress routes are always registered and active — a monolith-only install still needs vendors to reach Bazaar server-to-server.
- Media upload optimization (compress + convert to WebP) must run through exactly one shared mechanism reused by every upload point in the whole package (Item images in Epic 3, Hero Banner/Blog/Page in Epic 6, Store Info logo/favicon in this epic) — never a per-domain reimplementation. The original file is always retained as source; the optimized variant is a separate served variant, never an overwrite.
- An automated architecture test must be in place and passing (not just code-review discipline) asserting no domain's Models/Actions are used outside that domain's own namespace except through its Service — this is Definition of Done for every domain, not a one-off story.
- A `bazaar:status` Artisan command plus a Global Settings dashboard widget must self-check that the queue worker and scheduler cron are actually running (heartbeat), since these are required infrastructure for payment-timeout auto-cancel, review-deadline auto-complete, tokenized-link expiry, AWB retry, and notification dispatch elsewhere in the system.

## Technical Decisions

- Stack floor for this epic's scaffolding: PHP ^8.4, Laravel `illuminate/contracts` ^12.0||^13.0, Filament ^5.8, MySQL 8.x and PostgreSQL 15+ both first-class (no engine-specific SQL, no raw JSON functions — use Eloquent JSON casts).
- Package structure is domain-grouped (`src/{Domain}/{Models,Services,Actions,Enums,States,Events,Filament}`); call order is Service (entry point) → Action (multi-step escape hatch) → Model method (predicate only, never a mutating side effect). Presentation code (Filament Resource/Controller/Blade) may only call a Service, never reach into another domain's Model/Action directly — cross-domain calls always go through the target domain's Service, with Laravel Events for reverse-direction notification.
- User & Access module: Models User, Role, Permission, AuditTrail (AuditTrail subclasses `spatie/laravel-activitylog`'s Activity). Built on `spatie/laravel-permission` for Role/Permission. This module also hosts the cross-domain Approvals Inbox page (`User/Filament/Pages/ApprovalsInbox.php`) used starting in later epics — it is a read-only aggregation over each owning domain's Service, never a new domain or table; each owning domain exposes `pendingFor(User $staff): Collection<PendingApprovalItem>` as a shared DTO contract, gated by record-scoped Policy, not blanket role checks.
- Settings module: `spatie/laravel-settings` (never `config/*.php`) holds every runtime, Staff-editable operational parameter; `config/bazaar.php` holds only deploy-time/structural values (including Resource-class override seams). Never mix the two. Ships with `filament/spatie-laravel-settings-plugin` for the List+Edit UI plus the AD-17 health-check widget.
- Identifiers: every Model's primary key is a ULID (`HasUlids`), no exceptions, from this epic onward. (Human-readable transaction numbers via a shared `transaction_counters` table apply only to transactional entities introduced in later epics — not relevant to Epic 1's own models.)
- Four log-like mechanisms must stay fully separate and never merge: technical `Log::` output, `AuditTrail` (business mutation history, this epic), `NotificationLog` (Epic 2), `StaffNotification` (Epic 2, in-app alerts) — each its own storage and audience.
- Media pipeline: `spatie/laravel-medialibrary` conversions, hooked once and reused by every domain's upload point — not `Intervention Image` reimplemented per domain.
- Extension seams for client-specific behavior (only these three, never direct source edits): container-binding override on an interface, Laravel Events, or a config-registered Filament Resource class swap (`config('bazaar.resources.*')`).
- Money fields elsewhere in the system are whole-Rupiah unsigned bigint, never decimal/float — relevant if this epic's scaffolding touches any financial-adjacent settings (Min/Max Refund %).
- Package release discipline: semver via Composer/Packagist; migrations additive/non-destructive by default, breaking changes require a major bump plus documented upgrade path — relevant to how Story 1.1's install/migrate flow must behave for future upgrades.

## UX & Interaction Patterns

- Shell is constant across the whole product: fixed 250px sidebar + 62px topbar, built as a Filament panel theme override on DESIGN.md's tokens (primary `#00609e`, Poppins for headings/nav/buttons, Mulish for body, a 2px-stepped spacing scale, sm/md/lg/full radius scale) — never the stock Filament theme. Sidebar is domain-grouped; topbar carries global search, the Staff Notification bell, language/theme controls, and the user menu.
- Dual theme (light/dark) and bilingual (EN/ID) are both instant, no-reload, and persist per-User, toggled from the topbar user menu. Dark tokens are a net-new palette (luminance-inverted semantic pairs preserving hue family), never a literal color inversion. No chrome element may have a fixed pixel width that could clip a longer Indonesian string — use `white-space:nowrap` with content-driven padding everywhere.
- Core reusable components to build in this epic, used by every subsequent epic: Data Table (skeleton-row loading, pagination only — no infinite scroll, full-row tint for rows needing attention, row click opens detail, most-common action always a visible icon button never hidden in a menu), Modal/Dialog (one level only, focus-trap + Esc-to-close, reserved for short confirmations only), Toast (bottom-right stack, fires on every state-changing action without exception, ~4s auto-dismiss + manual close), Tabs (no-reload content switch, deep-linkable), Pagination, Alert Banner (danger/warn/info variants — info can never be dismissed since its underlying condition doesn't change), Empty State (icon + headline + optional CTA, distinct copy for "genuinely empty" vs "filtered to nothing"), Dropzone (uniform upload UI across all domains, always paired with a hint line stating the minimum requirement), Staff Notification Dropdown (340px panel, unread tint, "Lihat semua" footer link, deep-links to the source record via a Filament tab key anchor).
- Status Pills and the Attribute Reconcile Banner belong to later epics' data (Order/Catalog), but their generic patterns are established here: one pill per status value, text always alongside color (never color-only), and any maker-checker Approve/Reject control must be permission-gated at render (hidden, not disabled) for viewers lacking the specific approve-permission — labels are always generic ("Pending Approval"), never a hardcoded role name.
- Accessibility floor (internal-tool standard, not formal WCAG audit) applies to this epic's shell and every component in it: full keyboard operability (Tab + Enter/Space) with tab order matching visual order, accessible names on every icon-only control, visible native focus rings at AA-directional contrast even on dense table rows, disabled/auto-synced fields marked `aria-disabled`/`readonly` in addition to visual treatment.
- Responsive breakpoints apply to the shell built here: Desktop ≥1280px unchanged; Tablet 768–1279px collapses the sidebar to a 64px icon-only rail with tooltip labels; Mobile <768px turns the sidebar into an off-canvas drawer, collapses multi-column grids to one column, reflows table rows into stacked cards, and raises interactive tap targets to a 40px minimum (the one deliberate density exception).
- Banned interaction patterns everywhere, including this epic's own screens: infinite scroll, drag-and-drop reordering (use explicit move-up/move-down), decorative loading animation beyond standard skeleton/spinner, nested modals, color-only status meaning. A confirmation modal is reserved only for genuinely hard-to-reverse actions (e.g., deactivating a User, deleting a Brand/Category) — routine approve/reject actions fire immediately plus a toast, no extra confirmation step.
- Voice & tone: plain, literal, non-idiomatic in both EN and ID (e.g., "Item disimpan sebagai Draft" not celebratory/urgency language); every user-facing string needs both an EN and ID version, with no assumption that string lengths correspond 1:1 between them.

## Cross-Story Dependencies

- Story 1.2 (shell, tokens, component kit, bilingual/dual-theme, accessibility floor) is foundational to every other story in this epic and to every subsequent epic's UI — it should land early since 1.3–1.7's screens are built on top of it.
- Story 1.5 (Audit Trail) depends on mutations already occurring somewhere (Stories 1.3/1.4's Role/User CRUD are natural first sources to verify it against), and its automatic-capture mechanism must work with zero manual per-domain instrumentation for every domain built in every later epic.
- Story 1.3 (Role & Permission) must exist before Story 1.4 (Manage User) can enforce its "at least 1 Role required" rule.
- Story 1.6 (Global Settings) and Story 1.7 (Global SEO Defaults) share one surface; 1.7 is a section within 1.6, not a separate module.
- Story 1.10's shared media pipeline is a prerequisite for every image-upload point built in Epic 3 (Item) and Epic 6 (Hero Banner, Blog, Page) — it must be a stable, reusable mechanism by the time those epics start, not something they each reimplement.
- Story 1.1's package skeleton, domain-grouped module layout, and architecture test are the substrate every other domain (Epics 2–8) is built inside; the AD-5/AD-6 boundary enforcement it establishes governs all later work.
- Stories 1.8 and 1.9 (Service Layer / API Layer integration) expose whatever Services other epics build — they are thin integration surfaces, not gating dependencies for Epic 1's own stories, but later epics' Services must conform to the calling conventions these two stories establish.
